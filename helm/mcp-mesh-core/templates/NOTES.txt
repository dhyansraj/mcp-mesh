{{- $gf := dig "grafana" "config" (dict) (index .Values "mcp-mesh-grafana" | default dict) }}
{{- if and .Values.grafana.enabled (not $gf.existingSecret) (not $gf.adminPassword) }}

Grafana admin password was auto-generated. Retrieve it with:
  kubectl get secret {{ include "mcp-mesh-core.grafanaSecretName" . }} -n {{ .Release.Namespace }} \
    -o jsonpath='{.data.admin-password}' | base64 -d
The secret is reused on upgrade and, once this chart version has been applied,
never deleted by Helm (resource-policy: keep): Grafana applies a password only
on first start, so this secret is the only record of the one it is actually
running with. Helm reads that policy off the live object, so a release coming
from a chart that predates the annotation is protected only from the NEXT
upgrade onward — verify with:
  kubectl get secret {{ include "mcp-mesh-core.grafanaSecretName" . }} -n {{ .Release.Namespace }} \
    -o jsonpath='{.metadata.annotations}'
Grafana applies the generated value on first start only: if this release was
upgraded from chart <= 2.4.0 with persistence enabled, the previous admin
password remains active — see the chart README's upgrade notes.

GitOps note: generation uses `lookup`, which needs a live cluster. Rendering
without one (`helm template | kubectl apply`, Argo CD, Flux) produces a NEW
random password on every render, so this Secret never converges and syncing it
rotates the password. In those pipelines point the chart at a pre-created
secret instead:
  mcp-mesh-grafana.grafana.config.existingSecret=<secret name>
  mcp-mesh-grafana.grafana.config.generatedSecret=false
Adopt that in TWO steps on an existing release, never in the same change as a
chart bump: the annotation above has to be on the live secret first, or the
upgrade that sets existingSecret deletes the generated one. Then seal the
password retrieved above into the new secret — Grafana applies a password only
on first start, so with persistence enabled any other value has no effect until
the volume is reset.
{{- end }}
{{- $gfPersist := dig "grafana" "persistence" (dict) (index .Values "mcp-mesh-grafana" | default dict) }}
{{- if and .Values.grafana.enabled ($gfPersist.enabled | default false) }}

Grafana keeps its data (dashboards, annotations, users, and API keys authored
in the UI) on a claim that carries resource-policy: keep:

  PersistentVolumeClaim/{{ include "mcp-mesh-core.grafanaFullname" . }}-pvc

So `helm uninstall` leaves it in place and does NOT reclaim the storage — a
reinstall under the same release name picks the same volume back up, data
intact. Reclaim it deliberately with:
  kubectl scale deploy/{{ include "mcp-mesh-core.grafanaFullname" . }} -n {{ .Release.Namespace }} --replicas=0
  kubectl delete pvc {{ include "mcp-mesh-core.grafanaFullname" . }}-pvc -n {{ .Release.Namespace }}
(the scale-down is only needed while a pod still has it mounted). Helm reads
that policy off the live object, so a release coming from a chart that predates
the annotation is covered from the NEXT upgrade onward.

The bundled PostgreSQL volume behaves the same way for a different reason: it
is created by the StatefulSet's claim template, which the release does not own.
Tempo is the deliberate opposite: its trace buffer is an emptyDir by default,
so there is nothing to keep or reclaim, and a claim it is given explicitly is
still reclaimed on uninstall — it is under active retention, not durable
storage.
{{- end }}
{{- $tempoSub := index .Values "mcp-mesh-tempo" | default dict }}
{{- $tempoPersist := dig "tempo" "persistence" (dict) $tempoSub }}
{{- if and .Values.tempo.enabled ($tempoPersist.enabled | default false) }}
{{- $retention := dig "tempo" "config" "retention" "1h" $tempoSub }}

Tempo persistence is enabled, so this release owns a ReadWriteOnce claim:

  PersistentVolumeClaim/{{ include "mcp-mesh-core.tempoFullname" . }}-pvc

It is NOT annotated resource-policy: keep — `helm uninstall`, and any upgrade
that sets mcp-mesh-tempo.tempo.persistence.enabled back to false, deletes it.
That is deliberate: retention ({{ $retention }}) prunes the volume continuously,
so what it holds is minutes old and already expiring. The claim also constrains
rollouts — the outgoing pod must terminate before its replacement is scheduled,
or the replacement hangs on a Multi-Attach error.
{{- end }}
